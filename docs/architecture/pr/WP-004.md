## WP-004 — Persist score and gate result on outcome rows (ADR-002)

### Why
Every resolved outcome had `composite_score` and `validation_kappa` NULL, so neither the score nor
the judge gate could be tested against results. Production on 2026-11-15: 300 outcome rows, 252 with
NULL score, 285 with NULL kappa.

There were three causes:
1. **Seeder read the wrong field.** The daily seeder read the score from `gov_check.validation.composite_score`, where it never was. Discovery keeps it in `metadata.signal_score`.
2. **Portfolio composite never stored.** The portfolio composite was only in memory at save time; no column or metadata field kept it.
3. **Judge kappa overwritten.** The fact-checker **replaced** `gov_check` after the judge panel had written `gov_check.validation`, so every published rec lost its `aggregate_kappa` before save. Production confirms it: published rows have no `validation` key; only SUPPRESSED rows, which skip the fact-checker, keep it.

### What changed
- **`agents/rec_outcome_seeder.py`**: new `outcome_scores(rec)`, the one rule every seeding path uses.
  - Discovery score: `metadata.call_signal_score`, then `metadata.signal_score`.
  - Portfolio score: `composite_score`, then `metadata.composite_score`.
  - Legacy fallback: `gov_check.validation`.
  - Kappa: `gov_check.validation.aggregate_kappa`.

  The seeder now selects `is_discovery`.
- **`scheduler/orchestrator.py`**
  - Persists `metadata.composite_score` on saved recs.
  - Seeds the outcome row through `outcome_scores()`.
  - The outcome-seed swallow was `log.debug`; it is now WARNING and appends `outcome_seed <SYM>: …` to the run errors, so the run shows WARNING. A seed that returns False is recorded the same way.
- **`governance/fact_checker.py`** (outside `touches`; needed for kappa): `_keep_validation()` carries `gov_check["validation"]` into the replacement `gov_check` on all three replacement paths.
- **`agents/discovery_screener.py`** (outside `touches`; needed so the score is the call-time one): the INSERT path sets `metadata.call_signal_score`, which is never refreshed. `signal_score` is overwritten by re-confirmations and by the daily re-check (`discovery_rescorer.py`), so the 06:55 seeder was reading a later score.
- **`agents/paper_portfolio.py`**: `open_new_positions` drops `metadata.kind == "HOLDING_REVIEW"` recs and logs the count. Nothing sets that kind until WP-021, so this has no effect yet.
- **`scripts/backfill_outcome_scores.py`**
  - Dry run by default.
  - Fills only NULL fields, and the write is guarded with `.is_(col, null)`.
  - `--run` writes `logs/outcome_scores_backup_<ts>.json` before any update.
  - `--exclude-reconfirmed` leaves possibly drifted discovery scores NULL.
- **Tests**:
  - `tests/test_rec_outcome_seeder.py` (+13): `outcome_scores`; the seeder fills both fields for a discovery rec and a portfolio rec; the orchestrator seed path passes score and kappa, persists the composite, logs an exception at WARNING and records it, and records a False return.
  - `tests/test_outcome_tracker.py` (+1): the inserted row carries both fields.
  - New `tests/test_backfill_outcome_scores.py`: planning, dry run writes nothing, backup before apply, fill-only update, fact-checker carry-over on both paths, paper skip, discovery call score.

### The decision for the human running the backfill
183 of the 235 discovery rows have `metadata.last_confirmed_at`: the screener re-confirmed or the re-check re-scored them after the call, so their `signal_score` may be later than the score the call was made on. The original value can't be recovered. Options:
- **Default `--run`:** fills 235 rows. It meets the ≥150 bar, but 183 scores are only approximately call-time.
- **`--run --exclude-reconfirmed`:** fills only the 52 clean rows. It fails the ≥150 bar, but it's honest for calibration.

From today, new discovery calls carry `call_signal_score`, so this only affects history.

### Risk
Medium.
- Run status will show WARNING on days an outcome seed fails, which is the intent.
- `gov_check` on published recs gains a `validation` key. The dashboard reads named keys only.
- The backfill touches only NULL fields and has a backup.

### Rollback
Revert the PR. Restore `recommendation_outcomes` from the JSON backup in `logs/`: each entry is
`{id, composite_score, validation_kappa}` holding the values before the write, all NULL.
