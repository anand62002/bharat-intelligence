## WP-007 — Check the production schema against a code contract (ADR-005)

### Why
`recommendations.danger_drop_pct` was in `db/schema.sql` but never migrated, so every published
recommendation failed to insert for months. Migrations are applied by hand, and nothing compared
what the code writes with what production has. This is mechanism 3 of ADR-005.

### What changed
- **New `db/contract.py`**: `CONTRACT`, table → set of columns runtime code inserts or updates, for the 11 tables the plan lists.
  - Built from an AST scan of every `.table(...).insert/update/upsert`, plus the writes the scan can't see: `save_recs_node._DB_COLUMNS`, the discovery re-check's update dict, the outcome tracker's `f"price_t{h}"` horizon columns, and the long-horizon book.
- **New `scripts/check_schema.py`** (read-only): for each table it selects the contract columns with `limit 0`. PostgREST names one missing column per error (42703 or PGRST204), so the checker drops it and retries, collecting every gap.
  - A missing table is reported as `<table missing>`; any other error as `<error: …>`, never raised.
  - Prints one line per table and exits 1 if anything is missing.
- **`worker.py`: `startup_schema_check()`** runs once in `main()`, before the scheduler starts. It logs CRITICAL per missing column, carries on, and never raises.
- **`scripts/weekly_audit.py`: new `schema_contract` check.** Any gap is a FAIL.
- **Three broken writes fixed** (outside `touches`; found by the first production run, and the check can't pass without them):

  | Site | Problem | Fix |
  |---|---|---|
  | `agents/target_updater.py::_create_alert` | wrote `portfolio_alerts.portfolio_id`, a column that never existed (not in `schema.sql`) → **every target-updater alert (stop ratchet, target raised, protect gains, laggard review) failed to insert**, logged only as a warning | writes `holding_id`, the real FK column `portfolio_monitor` already uses |
  | `scheduler/orchestrator.py` P7-F data-quality alert | `"portfolio_id": None` → the alert never landed | key removed |
  | `agents/outcome_tracker.py` P6-D-8 sentiment flag | upsert with a non-existent `notes` column, on an `(agent_name, audit_date)` conflict target with no unique constraint → failed every time | plain insert like every other `agent_performance` writer; the explanation stays in the WARNING log |

- **New `tests/test_schema_contract.py` (16)**:
  - Every `save_recs_node._DB_COLUMNS` key is in the recommendations contract.
  - **An AST guard**: every literal column written to a contract table must be in `db/contract.py`, so the contract can't fall behind the code.
  - The three invented columns are no longer written.
  - Checker behaviour: one missing column, several found one error at a time, PGRST204 wording, a missing table, other errors, a healthy schema with one line per table, `limit 0` selects with only contract columns, exit codes.
  - The worker logs CRITICAL per gap, never raises, and runs the check before the scheduler.
  - The weekly audit check.

### Risk
Low.
- The script and start-up check only read.
- The three write fixes change alert and flag rows that were silently failing. They will now actually appear: expect target-updater INFO/WARNING alerts on the Portfolio tab again.

### Rollback
Remove the `startup_schema_check()` call from `worker.py`; the script is read-only. Reverting the three write fixes would bring the silent failures back.
