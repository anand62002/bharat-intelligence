## WP-013 — Write every screened symbol to the candidates ledger (ADR-002)

### Why
Discovery screens ~200 symbols a day but only promoted calls were kept, so there was no way to
test whether the pre-screen itself adds value, and only ~15 independent labels a month to learn
from. WP-012 created the `candidates` table; this fills it.

### What changed
- **New `data/candidate_ledger.py`**: `record_candidates(client, rows)`, a batched upsert
  on `(run_date, symbol, source)` (100 per batch), plus `screen_row()` / `deep_row()` builders,
  `nifty_level()` and `FEATURE_VERSION = 1`. It never raises. A missing table logs **one**
  WARNING naming `create_candidates.sql` and returns 0. Any other failure logs a WARNING and
  the run carries on. Rows are grouped by key set before batching, because PostgREST nulls absent
  keys across a batch and would otherwise wipe columns an update didn't mean to touch.
- **`agents/discovery_screener.py`**
  - `prescreen()` takes an optional `features` dict and fills it with what it already computed:
    price, RSI, above EMA200, PE, sector, sector PE, revenue growth, institutional %, DVM,
    triggers, filters passed, pass/fail, and a `skip_reason` (NO_OHLCV, INSUFFICIENT_DATA,
    EARNINGS_WINDOW, ILLIQUID, ERROR). Its return value is unchanged.
  - `run_discovery()`, after the pre-screen: one row per symbol in the slice (stage `SCREENED` or
    `PRESCREEN_PASS`), with the Nifty level fetched **once**. After deep analysis, the same keys
    are upserted with `agent_signals`, `signal_score` (the raw upside confidence, same as
    `metadata.signal_score`), `data_quality`, `tier`, `rec_id`; the stage becomes `DEEP`, or
    `PROMOTED` when a call was saved. Deep analysis also adds `composite_score`,
    `upside_pct` and `valuation_gap_pct` to `features`.
  - `save_to_db=False` (`--no-save`) writes no ledger rows and opens no client.
  - Returns a `DiscoveryList` (a `list` subclass, so callers are unaffected) with `.ledger_rows`.
    The count goes into the discovery `daily_runs` row as `details.candidates_written` and into
    the worker job's output.
- **`agents/multibagger_screener.py`**: each saved pick is recorded with `source='multibagger'`,
  stage `PROMOTED`, its score as `signal_score`, components in `features`, warren_bot's verdict in
  `agent_signals`. Dry runs record nothing. `candidates_written` added to the summary.
- `worker.py` (outside `touches`): the discovery job returns `candidates_written` too.
- `tests/test_discovery_screener.py`: the fixture's `prescreen` stub accepts `features`; the
  ledger is stubbed so these tests never open a client.

### Risk
Medium, as rated. The ledger writes sit in the discovery run but can't fail it: every path returns
a count and logs at WARNING. The extra cost is one Supabase client, one Nifty fetch and about three
upserts per run.

A same-day re-run overwrites that day's rows. That's correct because the key is per day.

### Rollback
Revert the PR. Rows already written are harmless.

### Follow-up noticed
`run_discovery(save_to_db=False)` still writes `daily_runs` and `discovery_runs` rows through
`_log_daily_run`, so a CLI dry run is not side-effect free. That's out of scope here.
