## WP-014 — Label candidate rows with 30- and 90-day alpha (ADR-002)

### Why
The candidates ledger (WP-013) records what was known at decision time. Without outcomes it
teaches nothing, and the outcome must be computed the same way as for published calls.

### What changed
- **`agents/outcome_tracker.py`**: the "price on a date" logic moved into one helper,
  `_close_near(hist, target_date, window)`. It strips the tz from yfinance's Asia/Kolkata index,
  drops the NaN partial bar and picks the closest close within ±4 days. `_fetch_price_on_date()`
  now uses it, with unchanged behaviour. The new `_batch_prices_on_date(symbols, date)` downloads
  many symbols in **one** yfinance call and applies the same helper, so there's still a single
  price-on-date definition.
- **`data/candidate_ledger.py` — `label_candidates(client, horizon_days)`**
  - It selects rows whose horizon has passed and whose `alpha_tN` is null, in pages of 500, with
    `.is_(col, "null")` and never `None` inside `.in_()`. Rows more than 60 days past their horizon
    are no longer retried (`LABEL_GIVE_UP_DAYS`), so delisted symbols aren't re-fetched every evening.
  - It does one batch download per run date (that day's ~200 symbols plus the Nifty).
  - **alpha = (price_t / price − 1) − (nifty_t / nifty − 1)**, as a fraction: the same formula and
    units as `recommendation_outcomes`. If a row has no entry Nifty, it uses the Nifty close on its run date.
  - A row with no entry price or no price at the horizon is **counted as failed and left null**,
    never labelled 0.
  - It writes `price_tN`, `nifty_tN`, `alpha_tN` and `labelled_at` through `record_candidates`
    (an upsert on the ledger key). Returns `{horizon, due, labelled, failed, errors}` and never raises.
- **`worker.py` — the 18:30 outcome-tracker job** labels t30 and t90 after the tracker and returns
  `candidates_labelled`, `candidates_label_failed` and the per-horizon detail, which lands in the
  job ledger's `details.output`. Like sentiment validation, it still runs when the tracker itself fails.
- `tests/test_worker_tracking.py` (outside `touches`): the existing "tracker fails, sentiment still
  runs" test now stubs the ledger client and checks labelling still runs.

### Risk
Medium. It adds about two batch yfinance downloads per run date that's due, roughly two a day at
steady state. Failures are counted and logged at WARNING and never fail the job.

### Rollback
Remove the labelling block from `job_outcome_tracker`. If needed, set `price/nifty/alpha_t30/t90`
and `labelled_at` back to null.
