## WP-005 — Record every worker job run in the job ledger (ADR-005)

### Why
No job recorded that it ran or what it produced. Every `job_*` in `worker.py` wrapped its body in
`try/except Exception: log.error(...)`, so a crash left nothing behind except a log line.
`daily_runs` held only the orchestrator's and discovery's own rows. This is mechanism 1 of
ADR-005, and the base for WP-006's missing-run and invariant alerts.

### What changed
- **`data/run_log.py`: `tracked_job(name, *, logs_own_row=False)`**
  - Times the job and catches any exception: it logs at ERROR with the traceback and never re-raises, so APScheduler keeps running.
  - Writes one `daily_runs` row with `pipeline=<name>`, through the existing `log_daily_run` (which also covers the case where the `pipeline` column is missing).
  - Status: `OK`; `WARNING` when the returned dict has non-empty `errors`; `FAILED` when the job raised.
  - Details:
    - `details.output` holds the returned dict, trimmed to 20 KB, largest values first.
    - The dict's `count` becomes `symbols_processed`.
    - `details.error` and `details.traceback` are filled on failure.
    - `details.llm_usage` holds the token counts.
  - A missing Supabase client logs a WARNING and the job still runs.
  - `logs_own_row=True` (orchestrator, discovery): those jobs already write their own row under the same name, so the ledger writes a row only on a crash. That records a crash before their own logging, without logging a success twice.
- **`data/llm_utils.py`: per-run token counter**
  - `llm_usage_scope()` and `record_usage(resp | body)`; `first_text()` now records usage.
  - It sits in a `ContextVar` holding a shared counter. Calls from the job thread, from `asyncio.run` and from `asyncio.to_thread` all count toward the job. Calls from bare `ThreadPoolExecutor` threads go to a process-wide `UNATTRIBUTED` counter rather than being lost.
- **`agents/sentiment.py`, `agents/market_digest.py`** (outside `touches`): their raw-HTTP Haiku calls don't go through `first_text`, so each gets one `record_usage(body)` line. Without it, the sentiment calls (the largest Haiku spend) would be missing from `llm_usage`.
- **`worker.py`: all 26 `job_*` functions wrapped** (the plan said 25).
  - Each drops its outer swallow and returns a dict with `count` (and `errors` where the job reports them).
  - Behaviour is unchanged where a job had independent steps:
    - The research agent's approval and merge gates still run if the scan fails.
    - The outcome tracker's sentiment validation still runs if tracking fails.
    - In both cases the main step's exception is held and re-raised afterwards, so the run is recorded as FAILED.
  - The options snapshot now handles NIFTY and BANKNIFTY separately, so one failing symbol no longer hides the other.
  - Log lines are unchanged.
- **Tests**:
  - New `tests/test_run_log.py` (16): FAILED row without propagating, OK with count, WARNING on errors, integer `errors`, None/list/dataclass results, trimming, missing client, insert failure, `logs_own_row`, LLM usage (SDK object, raw body, scope isolation, `to_thread`), fallback to base columns.
  - New `tests/test_worker_tracking.py` (13): every job wrapped with a unique name, own-row names match, at least 18 daily jobs, failing and returning jobs through real `worker` functions, the orchestrator not logged twice, held exceptions with secondary steps still running, options partial failure, breeze failure, no Supabase.

### Risk
Medium.
- About 25 more `daily_runs` rows per day, plus 4 per day for the portfolio monitor. Each row holds up to 20 KB of output.
- Jobs that used to be logged quietly now leave FAILED/WARNING rows. That is the intent, and WP-006 will alert on them.
- `job_*` functions now return dicts. APScheduler ignores return values, and `--now` calls them the same way.
- Readers of `daily_runs` that ignore `pipeline` see more rows. The orchestrator and discovery rows are unchanged; WP-001's check filters by `pipeline`.

### Rollback
Revert the PR. The decorator has no side effects beyond `daily_runs` inserts.
